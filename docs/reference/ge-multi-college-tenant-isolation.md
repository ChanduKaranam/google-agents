# Gemini Enterprise multi-college tenant isolation — research findings

## Executive summary

One GCP project can host five separate Gemini Enterprise "apps" (Discovery Engine `engines`) — quota headroom is enormous (150 engines / 100 data stores per project per location) — but a shared project is **not** a hard tenant-isolation boundary by itself. Google's own general multi-tenancy guidance treats "separate project per tenant" as the strongest isolation pattern and reserves shared-project multi-tenancy for cases where the application layer enforces isolation; there is no Discovery Engine– or Agent Engine–specific document that blesses "N apps, 1 project" as sufficient for hard tenant separation. The practical, well-supported answer for Job Helper Agent is a **hybrid**: keep one GCP project (`supadha-dev`) for cost/ops simplicity, but give every college its own Gemini Enterprise app, its own Data Store, its own deployed Agent Runtime instance (`reasoningEngine`), and its own IAM bindings scoped to that resource with `resource.name`/IAM Conditions — plus a defense-in-depth runtime check inside the ADK agent that reads the caller's email (which Gemini Enterprise does pass through) and refuses to answer if the caller's college doesn't match the deployed agent's college. The single biggest risk found: **Gemini Enterprise does not pass end-user identity to a custom agent by default** — you must explicitly configure `authorizationConfig` (an OAuth-based "tool authorization") on each registered agent, and forgetting to do so for even one college leaves that agent running as GE's own anonymous service identity with no way to tell users apart.

## 1. What isolation boundaries does Gemini Enterprise / Agentspace actually offer today?

**Per-app (engine) registration boundary.** A Gemini Enterprise "app" is a Discovery Engine `engine` resource (`projects/*/locations/*/collections/*/engines/*`). Each app can be bound to its own IAM policy: the API exposes `setIamPolicy`/`getIamPolicy` directly on `projects.locations.collections.engines`, i.e. per-engine (per-app) resource-level IAM bindings are a real, documented capability, not just project-wide roles. (https://docs.cloud.google.com/gemini/enterprise/docs/reference/rest/v1alpha/projects.locations.collections.engines/setIamPolicy)

**Data Store scoping.** Agent Search / Discovery Engine ships four predefined roles — `roles/discoveryengine.admin`, `roles/discoveryengine.editor`, `roles/discoveryengine.user`, `roles/discoveryengine.viewer` — described as granting access "to all discoveryengine resources" in a project; the access-control page does not itself describe a resource-scoped (per-data-store) grant pattern, only project-wide role grants, though custom roles are supported if the predefined roles are insufficient. (https://docs.cloud.google.com/generative-ai-app-builder/docs/access-control) Resource-level binding on individual engines (see above) is the documented workaround for scoping a Data Store's parent engine to a subset of principals.

**Reasoning Engine / Agent Runtime scoping.** Each deployed agent is its own `reasoningEngines/{ID}` resource. Access control for deployed agents runs through service accounts (default: `service-PROJECT_NUMBER@gcp-sa-aiplatform-re.iam.gserviceaccount.com`, granted `roles/aiplatform.reasoningEngineServiceAgent`) plus, for delegated end-user access, an OAuth-based "Agent Identity" mechanism. The docs for managing agent access explicitly note that **per-agent IAM bindings are not the default access model** — "the documentation does not describe per-agent or per-application IAM bindings [for the default service-account model]. Instead, access control operates at the project level through service account permissions" — but a **preview** feature called Agent Identity lets an agent be deployed with its own distinguishable IAM principal (`principal://agents.global.org-ORG_ID.system.id.goog/resources/aiplatform/projects/PROJECT_NUMBER/locations/LOCATION/reasoningEngines/AGENT_ENGINE_ID`), which can then be the target of per-agent `add-iam-policy-binding` calls. (https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/manage-agent-access, https://cloud.google.com/agent-builder/agent-engine/agent-identity)

**Sessions — IAM Conditions.** Agent Runtime Sessions expose a resource attribute, `aiplatform.googleapis.com/sessionUserId`, usable in IAM Conditions (CEL) to scope who can read/write session data:
```
gcloud projects add-iam-policy-binding PROJECT_ID \
    --member=user:userA@gmail.com \
    --role=roles/aiplatform.sessionViewer \
    --condition='api.getAttribute("aiplatform.googleapis.com/sessionUserId", "") == "userA"'
```
Roles: `roles/aiplatform.sessionViewer`, `sessionEditor`, `sessionUser`. This is useful for admin/operator access control over session data (e.g. "college A's IT admin can only inspect college A students' sessions"), not for the agent's own runtime data-access logic. (https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/sessions/iam-conditions)

**Google Workspace Group-based access scoping.** GE's sharing model supports granting access to a registered agent by "member type User/Group/Principal/Workforce pool/All users" — i.e. a Google Group can be the principal for an agent's `sharingConfig`, meaning "everyone in college-A-students@domain" can be granted access to college A's agent as a group, distinct from college B's group. This is console-only (no documented REST path for `sharingConfig` write), confirmed via the registration/manage docs. (https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/manage-agent-access)

**OAuth `authorizationConfig` / end-user identity propagation.** By default, **Gemini Enterprise authenticates to a registered agent using its own service identity and does not pass end-user information to the agent at all.** To change that, you register the agent with an `authorizationConfig.toolAuthorizations` array pointing at a previously-created `authorizations/{AUTH_ID}` resource:
```json
"authorizationConfig": {
   "toolAuthorizations": [
      "projects/PROJECT_NUMBER/locations/global/authorizations/AUTH_ID"
   ]
}
```
With this configured, GE prompts the end user for OAuth consent and forwards a resulting access/ID token to the agent. Separately — and this is the mechanism Job Helper Agent already benefits from — **ADK agents deployed via `adkAgentDefinition` on Agent Runtime receive the caller's email address from Gemini Enterprise even without configuring `authorizationConfig`**: "ADK agents receive the user's email address from Gemini Enterprise. This allows agents to recognize individual users..." (https://docs.cloud.google.com/gemini/enterprise/docs/register-and-manage-an-adk-agent). This matches independently-observed runtime behavior already logged in this project's `gemini-enterprise-agents` skill: a live probe agent saw a real end-user email as `user_id`, not a `default-user-id` fallback (verified 2026-07-22, live deployed agent + session event log).

Contrast: an agent registered via `a2aAgentDefinition` (the A2UI path) receives **no** identity at all — "no identity header, no message metadata, no authenticated principal" — per the same project's live-tested findings. This is a load-bearing distinction: Job Helper Agent must stay on the `adkAgentDefinition` / Agent Runtime registration path to keep getting caller identity.

## 2. Is "one project, N apps" sufficient, or does Google recommend separate projects per tenant?

There is **no Discovery-Engine- or Agent-Engine-specific "multi-tenancy" doc** that explicitly blesses or forbids the one-project/N-apps pattern; the closest first-party framing is Google Cloud's general resource-hierarchy and multi-tenancy guidance, which is service-agnostic:

- Google's landing-zone / resource-hierarchy guidance: folders "provide isolation boundaries between projects" and should be used "to isolate requirements for different departments and teams," including modeling "different legal entities, departments, and teams" — colleges under one umbrella institution map naturally onto this pattern. IAM roles granted at a folder are inherited by everything under it. (https://docs.cloud.google.com/architecture/landing-zones/decide-resource-hierarchy, https://docs.cloud.google.com/resource-manager/docs/cloud-platform-resource-hierarchy)
- Google's Cloud Run multi-tenancy guidance (the clearest first-party statement found on the shared-project-vs-per-tenant-project trade-off, though written for a different product) frames project-per-tenant as the strongest isolation available on GCP and explicitly separates first-party code/projects from tenant/customer-code projects into different folders when the two need different trust levels. (https://docs.cloud.google.com/run/docs/securing/multi-tenant)
- IAM's own resource-hierarchy access-control doc confirms the mechanical fact underlying all of this: project-level IAM bindings apply to *everything* in the project unless a resource explicitly supports (and you use) resource-level IAM — which, per §1 above, Discovery Engine `engines` and Agent Engine sessions *do* support, but Data Stores are not documented as supporting resource-level bindings. (https://cloud.google.com/iam/docs/resource-hierarchy-access-control)

Net: Google's own guidance is "the stronger the isolation you need, the more you should reach for separate projects (or at minimum separate folders)," but this is general GCP doctrine, not a Discovery-Engine-specific mandate, and Discovery Engine/Agent Engine *do* offer meaningful resource-level primitives (per-engine IAM, per-session IAM Conditions, per-agent Agent Identity in preview) that reduce — but do not eliminate — the gap between "one project" and "hard isolation."

## 3. Defense-in-depth: scoping data access so College A's agent can't read College B's data even under adversarial input

- **Data Store IAM**: as noted in §1, the documented Discovery Engine roles are project-wide; there is no documented per-data-store metadata-filtering ACL mechanism analogous to row-level security. The practical isolation primitive is: **one Data Store per college**, referenced only by that college's Search/RAG tool configuration, with that college's engine's IAM policy (via `engines.setIamPolicy`) restricted to that college's users/group. A single shared Data Store with a `college` metadata field and query-time filtering is *possible* in principle (Discovery Engine supports metadata filters on search requests) but was not found documented as an access-control mechanism — it is a query-time filter that a compromised or buggy prompt could omit, so it does not meet a "no invention, no leakage even under adversarial input" bar. Per-Data-Store separation is the safer primitive because omitting a filter can't leak data that isn't there.
- **ADK session state**: ADK sessions are addressed by `(app_name, user_id, session_id)`; `VertexAiSessionService` is Google's recommended production session backend for Agent Engine deployments. (https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/sessions/manage-with-adk) Because each deployed agent is registered under its own `reasoningEngines/{ID}` (which functions as ADK's `app_name` when deployed), **sessions from one college's deployed agent instance are structurally unreachable from another college's deployed agent instance** — they are different `app_name`s served by different backend resources, not rows in a shared table an errant query could cross. This is the strongest naturally-occurring isolation boundary in the whole stack, *provided each college gets its own deployed agent rather than sharing one deployment with a college parameter in the prompt.*
- **Agent Engine Memory Bank**: Memory Bank scopes memories by an arbitrary key-value `scope` object, defaulting to `{"user_id": USER_ID}` unless a scope is explicitly provided; each `reasoningEngines/{ID}` has its own Memory Bank namespace ("The Memory Bank scopes memories to a user, which can then be accessed by any authorized agent interacting with that user" within a given engine). (https://cloud.google.com/agent-builder/agent-engine/memory-bank/overview) Same conclusion as sessions: if each college is a separate `reasoningEngines/{ID}`, Memory Bank isolation is structural (different engine = different memory store entirely), not merely a filter that could be bypassed by a scope-key typo.
- **Bottom line for defense-in-depth**: the single design choice that buys the most real isolation, cheaply, is **one Data Store + one deployed Agent Runtime instance (`reasoningEngines/{ID}`) per college**, rather than one shared deployment branching internally on a "college" variable. A shared deployment turns every one of Sessions/Memory Bank/Data-Store isolation from "structural" into "a filter condition the LLM or a tool bug could omit" — exactly the adversarial-input failure mode the requirement is trying to rule out.

## 4. Reading caller identity inside ADK agent/tool code at runtime

Two documented/observed mechanisms, both usable to enforce per-college authorization inside the agent's own code (defense-in-depth on top of IAM):

1. **Default path (no `authorizationConfig` needed), already true for Job Helper Agent's `adkAgentDefinition` registration**: Gemini Enterprise passes the end user's email as ADK's `user_id`. This was independently verified live for this project (2026-07-22 probe: `user_id` was a real email, not `default-user-id`), and is now also documented: "ADK agents receive the user's email address from Gemini Enterprise." (https://docs.cloud.google.com/gemini/enterprise/docs/register-and-manage-an-adk-agent) In ADK/tool code this is reachable as `ToolContext`/`ReadonlyContext.user_id` (`ctx.user_id` per this project's own skill notes on ADK 2.4.0's `Context` API), or via `callback_context.state`/session object depending on where the check runs.
2. **OAuth path, when `authorizationConfig` is configured**: Gemini Enterprise performs 3-legged OAuth via its "Agent Identity auth manager," then forwards a token the agent can inspect. In tool code this surfaces as `tool_context.auth_response.get("id_token")`, decodable as a JWT to read `email` and other claims (SECONDARY SOURCE, community discussion, consistent with the official Agent Identity overview's description of the auth-manager/credential-broker flow — the discussion itself is not a Google doc): https://github.com/google/adk-python/discussions/3488, corroborated by the official overview at https://docs.cloud.google.com/gemini-enterprise-agent-platform/govern/agent-identity-overview which confirms the auth-manager brokers and decrypts end-user credentials for the agent but stops short of giving exact field names.

**Recommended runtime check for Job Helper Agent**: since each college gets its own deployed agent (per §3), the simplest, most robust check is *not* "does this email belong to college A" (fragile — requires maintaining a roster or domain allowlist per agent) but rather relying on the email-domain convention colleges already have (e.g. `@medicalcollege.edu`, `@womenscollege.edu`) as a cheap sanity check in a `before_agent_callback`, logging/refusing on mismatch — while the *real* isolation guarantee comes from the college never being able to reach the wrong deployed agent in the first place (IAM + sharing scoped per app, per §1/§5). Treat the in-code email check as a second belt, not the primary isolation mechanism — GE's identity propagation is a Preview/documented-but-thin surface and should not be the only thing standing between College A and College B's data.

## 5. IAM / org-policy patterns for segmenting by Google Workspace Group or OU, one project

- **Group-based sharing per app**: GE's agent-sharing UI supports "User/Group/Principal/Workforce pool/All users" as the member type when granting access to a specific registered agent — so `college-a-students@tilicho.in` (a Google Group) can be the sole principal shared on college A's agent, and a different group on college B's. This is console-only; no documented REST/`gcloud` path for writing `sharingConfig` was found (read-only via the agents list API). (https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/manage-agent-access)
- **Service accounts per college**: nothing prevents deploying each college's `reasoningEngine` under a distinct custom service account (rather than the shared default `service-PROJECT_NUMBER@gcp-sa-aiplatform-re.iam.gserviceaccount.com`) and IAM-binding each service account to only that college's Data Store/engine — the manage-agent-access doc explicitly lists "custom service accounts with assigned IAM roles" as one of the four supported agent-auth models. Combined with the **Agent Identity (Preview)** feature — which mints a distinguishable per-agent IAM principal — this gets close to per-tenant service-account isolation without separate projects. (https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/manage-agent-access, https://cloud.google.com/agent-builder/agent-engine/agent-identity)
- **Resource-level IAM bindings on Data Stores/engines/apps**: engines support `setIamPolicy`/`getIamPolicy` directly (§1); Data Stores were not found to support resource-level IAM in the fetched access-control doc — the only per-college binding surface documented for Data Stores is indirect, through the engine(s) that reference them, or through separate Data Stores each behind its own engine's IAM.
- **VPC Service Controls**: relevant to *exfiltration/perimeter* security (blocking public internet access to a project's Vertex AI/Discovery Engine APIs from outside an approved network), **not** to tenant-vs-tenant access control within the same project — a VPC-SC perimeter wraps the whole project (or an org's projects) as one boundary; it does not distinguish College A's traffic from College B's traffic once both are inside the perimeter. Confirmed by the general Vertex AI VPC-SC doc describing perimeters as protecting "the resources and data you specify" at the project/API level, not at a sub-project or per-app level. (https://cloud.google.com/vertex-ai/docs/general/vpc-service-controls) **VPC-SC is not the tool for this problem.**

## 6. Recommended architecture and trade-offs

**What Google's own docs/architecture guidance points toward**: general GCP guidance (landing-zone/resource-hierarchy, Cloud Run multi-tenancy) leans toward separate projects (or at least separate folders) as the strongest isolation, reserving shared-project multi-tenancy for cases where application-layer + resource-level controls are deliberately engineered in. No Discovery-Engine/Agent-Engine-specific doc either recommends or rules out one project for several tenants; the product *does* supply real resource-level primitives (per-engine IAM, per-session IAM Conditions, per-agent Agent Identity, per-agent group-based sharing) that make "hard-ish" isolation achievable within one project, short of what a separate-project boundary gives for free (fully separate IAM policy root, fully separate quota, fully separate billing/blast radius, no possibility of a project-wide role accidentally spanning tenants).

**Trade-off synthesis (my own, not from Google docs)**:

| Option | Isolation strength | Cost/ops overhead | Notes |
|---|---|---|---|
| (a) 1 project, N isolated GE apps/engines + per-app IAM + runtime identity check | Good, not absolute — a project-wide IAM role (e.g. a future `discoveryengine.admin` grant for an ops purpose) spans all colleges unless carefully scoped down | Low — one billing account, one deploy pipeline, one place to patch/update shared code | Quota is a total non-issue: 150 engines / 100 data stores per project vs. 5 colleges needed |
| (b) N separate GCP projects, one per college, shared tooling/code | Strongest — separate IAM root, separate quota, separate blast radius, a leaked project-wide role in one project cannot touch another | Higher — 5x billing accounts or careful shared-billing setup, 5x IAM setup, 5x monitoring/logging silos, deploy tooling must parameterize project ID everywhere | Matches Google's general multi-tenancy doctrine most closely |
| (c) Hybrid: 1 project, N apps, but *also* per-college service accounts / Agent Identity, group-based sharing, and a belt-and-suspenders in-agent identity check | Close to (b) at much lower overhead | Low-moderate | Recommended below |

**Recommendation for Job Helper Agent / `supadha-dev`**: **(c), the hybrid**, because at 5 tenants the operational cost of 5 separate projects (billing, IAM setup, monitoring, deploy pipeline parameterization) is disproportionate to the marginal isolation gained, given that Discovery Engine/Agent Engine's resource-level primitives (per-engine IAM, per-`reasoningEngine` sessions/Memory Bank isolation, per-agent sharing by Google Group) already deliver *structural* separation for the data planes that matter most (sessions, Memory Bank, and — if each college gets its own Data Store — RAG data too). Revisit toward (b) only if: a college needs its own billing relationship/legal boundary, or an audit/compliance requirement specifically mandates separate GCP projects per tenant, or the number of colleges grows enough that a single project's shared quotas or a single mis-scoped IAM grant becomes an unacceptable blast radius.

### Concrete next steps for `supadha-dev`

1. **One GE app (engine) per college**, not one shared app — five `projects/*/locations/global/collections/*/engines/*` resources, each with its own `sharingConfig` scoped to that college's Google Group, set via the console (no documented REST write path).
2. **One Data Store per college**, referenced only by that college's app/agent — avoids relying on a metadata filter as the only thing standing between colleges' RAG data.
3. **One deployed Agent Runtime instance (`reasoningEngines/{ID}`) per college**, registered via `adkAgentDefinition` (never `a2aAgentDefinition`, which drops identity entirely) — this is what makes Sessions and Memory Bank isolation *structural* rather than filter-based.
4. **Per-engine IAM**: run `engines.setIamPolicy` on each college's engine, restricting Discovery Engine User role grants to that college's group; do not rely solely on project-wide `discoveryengine.user`.
5. **Per-college service accounts** for each deployed agent (rather than sharing the default Reasoning Engine Service Agent across all five), each IAM-bound only to its own Data Store/engine — reduces blast radius if one college's agent is ever compromised or misconfigured.
6. **Code change in the ADK agent** (`agent.py` / a shared `before_agent_callback`): read `ctx.user_id` (the caller's email, populated by GE automatically for `adkAgentDefinition` registrations — no `authorizationConfig` needed for this) and compare its domain against an allowlist baked into that college's specific deployment config (env var, not shared code path); refuse and log on mismatch. This is a defense-in-depth check, not the primary isolation boundary — the primary boundary is #1–#3 (the caller physically cannot reach the wrong `reasoningEngine`/engine because it was never shared with them).
7. Treat `authorizationConfig`/full OAuth delegation as optional for now — Job Helper Agent doesn't call user-owned third-party APIs (Jira, GitHub, BigQuery-with-end-user-creds) where 3-legged OAuth is the documented use case; the email-passthrough GE already does for `adkAgentDefinition` agents is sufficient for the per-college check in #6.
8. Do **not** reach for VPC Service Controls for this problem — it protects the project's perimeter from the public internet, not College A from College B inside the same project.
9. Revisit this decision if any college needs separate billing, a compliance mandate names "separate project per tenant" explicitly, or the college count grows past what a single project's shared operational surface (one IAM policy root, one on-call rotation, one quota pool) can comfortably carry.
